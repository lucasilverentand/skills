# Product docs and user guides
Use for: end-user (non-developer) documentation: help-center and knowledge-base articles, task-based guides and walkthroughs, onboarding docs, FAQs, help articles shown in-app and feature docs.

## Gather first
- **Task and reader:** the goal in users' words, from support tickets, feedback or the brief; the audience (beginner, power user or admin); and the required plan, role or permission and platform. Return unsettled audience, tone or brand voice to the lead with options and a recommendation.
- **Shipped facts:** UI labels, menu paths, limits, prices and behavior from the actual product, build, source strings or accepted designs, with their release. Never invent one; return anything unconfirmed to the lead as unverified.
- **Existing articles** on the task, and the destination's conventions.

## Structure
For task articles; for FAQs and feature overviews, keep only the parts the reader needs.
1. **Title and intro:** the task in users' words ("Export your invoices", or "How do I…" if the destination uses questions), then what the reader will achieve.
2. **Before you start:** required plan, role, platform, version and setup, if any.
3. **Steps:** numbered, one action each, with the menu path and what the reader sees next. Separate platforms under labeled headings.
4. **Check it worked:** what success looks like, then the next likely task.

Troubleshooting: title the symptom, then problem → cause → solution, ending with where to get help. Onboarding: first-run essentials first, advanced options later. In-app help panels: lead with the answer and link the full article.

## Rules
- Write plain second-person, present-tense text that assumes no code knowledge. Define terms on first use; avoid jargon and "simply". Never blame the user.
- Quote UI labels exactly as shipped, including capitalization. If only designs exist, flag that labels may change.
- Text carries every step. Add visuals only where location or state is hard to describe, each with alt text, no personal data and its release noted so it can be kept current.
- Write FAQs only for questions users actually ask, sourced from tickets, feedback or search logs; never invent them.
- Describe current shipped behavior; label beta or upcoming features as the destination does. Never promise dates, prices or limits.
- Record version and last-reviewed date in the destination's native fields, if any; impose no template or footer it lacks.

## Check before handing back
- Where the brief permits, walk the steps in the product or build. Report which you performed, which you checked only against designs or source, and which are unverified.
- Labels, paths and visuals match the stated release; every troubleshooting path ends in a fix or support route.
- A reader at the stated level could finish unaided. Run the project's existing docs checks, if any; add no tooling.

## Boundaries
Developer tutorials, API reference and UI microcopy (button labels, tooltips, error strings) are out of scope. Document the product as it is; return suggested product changes to the lead as proposals. Save in the project's user-docs home ([knowledge-and-planning.md](../knowledge-and-planning.md)), updating an existing article rather than creating a parallel one; write no run report.
