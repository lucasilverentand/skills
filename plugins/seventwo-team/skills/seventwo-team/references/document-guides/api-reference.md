# API reference
Use for: reference documentation for HTTP, GraphQL and RPC APIs and webhooks: authentication, operations, errors, limits, pagination, idempotency, versioning, deprecation, migration notes and short SDK quickstarts. Integrators treat every documented field, limit and error as a promise.

## Gather first
- **Source of truth:** schema and code: OpenAPI, GraphQL SDL, protobuf, routes, validation and auth middleware. Prefer reference generated by the project's own tooling; edit the annotations it reads, not its output.
- **Coverage:** compare routes or schema with the docs. List undocumented, stale and removed operations in your handoff, not a separate report.
- **Real facts:** environments, auth schemes and scopes, limits, error codes, webhook signing, deprecation policy and which SDKs exist. Never invent an endpoint, field, limit, error code or behavior. Mark anything unverified and return it to the lead.

## Structure
1. **Overview:** purpose, base URLs per environment, versioning scheme, shared conventions.
2. **Authentication:** scheme, obtaining and sending credentials, scopes, auth failures.
3. **Operations:** per operation, purpose; method and path or operation name; auth and required scopes; parameters with type, required or optional, default and constraints; request and response schemas with examples; every error with cause and fix; behavior notes such as pagination, idempotency and side effects.
4. **Errors:** glossary by code with meaning, cause, fix and whether to retry.
5. **Limits and patterns:** rate limits and headers, pagination, idempotency keys.
6. **Webhooks:** events, payload schemas, signature verification, acknowledgement (expected status and deadline), retries, ordering, duplicate delivery and replay protection, as actually implemented.
7. **Changes:** deprecations with dates and replacements, changelog, migration notes.
8. **Quickstarts:** a short first call per primary SDK, linking to reference entries.

## Rules
- Keep reference neutral, complete and consistent: one template, terminology and ordering for every operation. Link to tutorials and conceptual explanation instead of including them.
- Examples run as pasted: curl plus the project's primary SDK languages, realistic fake data, placeholders such as `<API_KEY>`. Never include real keys, tokens or customer data.
- Pair each request with its response, including an error response.
- Describe current behavior as current; label beta, planned and deprecated behavior.
- Use existing generators, schema validators and tests; otherwise verify by reading the source.

## Check before handing back
- Every operation in the code or schema is documented or listed as internal, and every documented operation exists.
- Validate examples against the schema. Run them in a sandbox or tests only where the brief permits. Report which ran, which were schema-checked only, and which remain unverified.
- For auth, scope or signature guidance, ask the lead for a [security/privacy](../presets/security-privacy-reviewer.md) read.

## Boundaries
When docs and implementation disagree, report the discrepancy to the lead with evidence (file, line, observed response); do not silently fix either. A public API is a contract with outside consumers, so changing documented behavior needs a product decision and independent review under SKILL.md's review rules. End-user help articles, step-by-step tutorials and UI microcopy are out of scope. Save into the project's existing API docs home ([knowledge-and-planning.md](../knowledge-and-planning.md)) and update existing pages rather than creating parallel ones.
